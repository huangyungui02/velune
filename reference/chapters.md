# 沉浸式互动机制

## 章节（chapters）

### 结构

* title: 章节标题（前端显示）
* subtitle：章节概要（面向用户说明，前端显示）
* role：AI在该章节扮演的角色
* task：AI在该章节的任务

### 目标

在与某位 souler 的对话中，同时支持两种模式：

* 自由聊天
* 章节体验

章节不是唯一入口，而是会话的一种上下文：

* `session` 可以绑定 `chapter_id`
* 也可以不绑定 `chapter_id`
* 同一个 chapter 可以被用户反复体验
* 不同 session 可以拥有相同的 `chapter_id`
* 自由聊天与章节体验共用同一个 `sessions` / `messages` 主链路

### session模式

#### 自由聊天

* `chapter_id = null`
* 用户直接在输入框发送第一条消息时创建 session
* `session.title` 由 AI 根据首轮内容总结

#### 章节体验

* `chapter_id != null`
* 用户点击某个 chapter 的开始按钮时创建 session
* `session.title` 直接使用 `chapter.title`

### 后端chapters表结构
* id
* souler_id
* seq (int, auto increase)
* title
* subtitle
* role
* task
* created_at
* updated_at

### 其他表格修改
sessions：新增可空 `chapter_id` 字段

### soulers表补充字段

为控制 chapters 生成状态，在 `soulers` 表增加：

* `chapters_status`
  + `pending`
  + `processing`
  + `complete`
  + `failed`
* `chapters_generated_at`
* `chapters_error`

### 数据约束与索引

建议增加：

* `chapters (souler_id, seq)` 唯一约束
* `chapters (souler_id, seq)` 索引
* `sessions (user_id, chapter_id, updated_at desc)` 索引

### 生成规则

#### 生成入口

`chapters` 生成应作为独立流程，不应由 chat 接口顺手触发。

#### 幂等与并发控制

需要满足：

* 同一时刻，同一个 souler 只能有一个 `chapters` 生成任务处于 `processing`
* 如果某个 souler 的 `chapters_status = complete`，则前端不再提供重复生成入口
* 如需重生成，后续只允许后台人工操作，不开放给普通用户

#### 失败恢复

生成失败时：

* `chapters_status` 写为 `failed`
* 写入 `chapters_error`
* 不应留下半套可见的 chapters 数据

因此推荐流程为：

1. 原子检查 `souler.chapters_status`
2. 更新为 `processing`
3. 生成完整 10 章
4. 一次性写入 chapters
5. 更新为 `complete`
6. 写入 `chapters_generated_at`

## 用户chat流程

当用户打开某位 souler 的 `ChatView` 时：

* 下方始终保留输入框
* 只有当当前聊天界面为空时，才显示章节区域
* 用户可以直接输入，进入自由聊天
* 也可以点击某一章开始，进入章节体验

### 章节区域

只有当当前聊天界面的 `messages.isEmpty` 时，前端才显示章节区域，并查询该 souler 是否已经有 chapters：

+ 如果没有，显示“生成chapters”按钮和界面，点击后，后端开始生成chapter
+ 如果该 souler 的 `chapters_status = processing`，显示“生成中”状态，不可重复点击
+ 如果该 souler 的 `chapters_status = failed`，显示失败状态和重试入口
+ 如果该 souler 的 `chapters_status = complete`，按顺序显示每一章的 `title` 和 `subtitle`

一旦当前聊天界面的 `messages.isEmpty == false`：

* 章节区域立即隐藏
* 界面切换为普通会话态
* 不再在当前界面中展示章节入口

### 自由聊天模式

当用户未点击任何 chapter，而是直接在输入框发送第一条消息时：

* 创建一个新的自由聊天 session
* `chapter_id = null`
* 系统提示词仅使用 `souler` 风格，不注入 chapter 信息
* `session.title` 由 AI 根据首轮对话生成

### 章节体验模式

当用户点击某一个 chapter，并点击开始：

查询 `chapters` 表对应的 `title`, `subtitle`, `role`, `task`，以及 `souler_name` 拼接提示词为系统提示词：
```markdown
# 人物
以{souler_name}的风格和用户进行沉浸式互动

# 章节
{title}

## 章节概要
{subtitle}

# 本章角色
{role}

# 任务
{task}

# 输出格式
每次回复都需要同时生成两部分内容：
1. 面向用户展示的正文 `output`
2. 四个用户下一步可能进行的操作或回答 `options`

注意：
- `output` 是主要回复内容，供前端流式展示
- `options` 必须与本轮 `output` 同时生成，但应作为独立结果返回
- `options` 必须是四条简短、可点击、可直接作为用户发言的文本
- 不要输出额外解释

# 结束对话
如果你的任务已完成，你可以总结并主动与用户结束对话。
```

### 会话启动方式

章节会话通过独立接口启动，而不是复用普通发送消息接口。

建议增加独立接口：

* `start chapter session`

职责：

* 校验 chapter 存在且属于该 souler
* 创建一个新的 session
* 写入 `chapter_id`
* `session.title = chapter.title`
* 以该 chapter 的系统提示词生成一段开场白
* 将这段开场白作为 session 的第一条 `assistant message`
* 同时返回本轮的四个 `options`

说明：

* 开场白不需要插入任何虚拟的 `user message`
* 每次点击开始，都会创建新的 session
* 同一个 chapter 可以反复开始，形成多个 session

### 持续互动方式

用户进入任意已开始的 session 后：

* 可以点击 `options`
* 也可以在输入框发送消息
* 两者都作为普通 `user message` 写入 `messages`

AI 回复时：

* 回复正文必须走 streaming
* `options` 与该轮正文同时生成
* `options` 不需要逐 token 流式返回，可以在正文生成结束后一次性作为一个 streaming 事件返回

### SSE返回协议建议

不要让模型直接向前端流式输出 JSON 文本。

原因：

* 正文需要自然流式展示
* JSON 增量输出很脆弱，前端难以稳定解析
* 一旦 JSON 不完整，本轮直接失败

因此推荐将正文与 options 拆为两个 SSE 事件：

1. `delta`
  + 流式返回正文片段
2. `options`
  + 一次性返回四个 options
3. `done`
  + 返回 session 完成信息

示意：

```json
{ "type": "delta", "delta": "..." }
```

```json
{ "type": "options", "options": ["...", "...", "...", "..."] }
```

```json
{ "type": "done", "sessionId": "...", "title": "..." }
```

### 历史记录策略

如果AI继续回复用户时，当前session的messages数量超过20，则历史记录只取最近20条messages。

说明：

* 这条策略继续保留
* 历史列表的展示方式保持原样，不按 chapter 分组重构
* 历史列表中不额外显示“第 N 章”等 chapter 标签
* `options` 先不持久化到数据库
* 历史会话只保留真实 `message`
* 当用户再次发送消息时，再重新生成本轮新的 `options`

### 费用策略

建议：

* `start chapter session` 视为一次完整 AI 调用，消耗一次 chat credit
* 后续每轮持续对话，仍按当前 chat 计费策略执行

这样计费模型更统一，也更容易实现。
