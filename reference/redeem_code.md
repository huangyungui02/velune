# 兑换码设计

## 目标

为 app 增加一个简单、稳定、可审计的兑换码能力。

每个兑换码：
- 可以被多个用户使用
- 有总使用次数上限
- 兑换成功后，一次性发放固定数量的 `stardust`
- 同一用户对同一个兑换码只能成功兑换一次
- 必须登录后才能兑换

适合的场景：
- 活动拉新
- 节日赠送
- 社群福利
- 灰度补偿

不适合的场景：
- 一码一人卡密
- 随机奖励
- 复杂渠道结算
- 多种权益混合发放

---

## 推荐模型

不要单独做第二套余额系统。

直接基于现有 `billings.credits` 发奖励：
- 兑换成功后，直接给用户当前 `credits + reward_credits`
- `reward_credits` 即这张兑换码的一次性奖励，例如 `500`

这样做的原因：
- 现有消费逻辑已经全部围绕 `billings.credits`
- chat / echo 无需知道“这部分余额来自订阅还是兑换码”
- 不需要改消费链路，只需要在兑换成功时做一次加账
- 风险更低，维护成本更小

---

## 数据结构

### 1. redeem_codes

定义兑换码本身。

建议字段：
- `id`
- `code`
- `reward_credits`
- `max_redemptions`
- `redeemed_count`
- `is_active`
- `starts_at`
- `expires_at`
- `created_at`
- `updated_at`

字段含义：
- `code`：用户输入的兑换码，建议统一转大写保存与比较
- `reward_credits`：奖励的 `stardust` 数量，例如 `500`
- `max_redemptions`：总可兑换次数，例如 `500`
- `redeemed_count`：当前已兑换次数
- `is_active`：后台开关，便于随时停用
- `starts_at` / `expires_at`：控制生效期

约束建议：
- `code` 唯一
- `reward_credits > 0`
- `max_redemptions > 0`
- `redeemed_count >= 0`
- `redeemed_count <= max_redemptions`

---

### 2. redeem_code_redemptions

记录每一次成功兑换。

建议字段：
- `id`
- `redeem_code_id`
- `user_id`
- `reward_credits`
- `redeemed_at`

作用：
- 防止同一用户重复兑换
- 保留审计记录
- 支持后续活动复盘
- 支持客服排查

关键约束：
- `unique (redeem_code_id, user_id)`

这条唯一约束非常重要。

它是“同一个用户不能重复兑换同一个码”的最终兜底。

## 兑换规则

### 成功条件

兑换成功需要同时满足：
- 用户已登录
- 兑换码存在
- 兑换码处于启用状态
- 当前时间在可用时间范围内
- `redeemed_count < max_redemptions`
- 当前用户没有成功兑换过这个码

### 成功结果

兑换成功后：
- 写入一条兑换记录
- 对应兑换码的 `redeemed_count + 1`
- 用户 `billings.credits + reward_credits`
- 返回最新余额

### 失败结果

建议明确区分以下失败原因：
- `UNAUTHORIZED`
- `CODE_NOT_FOUND`
- `CODE_INACTIVE`
- `CODE_NOT_STARTED`
- `CODE_EXPIRED`
- `CODE_LIMIT_REACHED`
- `ALREADY_REDEEMED`

这样前端文案会更干净，也方便后续排查。

---

## 并发与超发

这是整个设计里最重要的点。

如果一个码只剩最后几个名额，多个用户同时兑换，必须保证不会超发。

推荐做法：
- 在数据库里用一个原子事务完成整个兑换流程
- 先锁定目标兑换码记录
- 校验剩余次数
- 写入 redemption 记录
- 增加 `redeemed_count`
- 增加用户 `credits`

核心原则：
- 库存判断和扣减必须在同一个事务里完成
- 不能先查还有名额，再在应用层单独更新

否则高并发下会超发。

---

## 为什么不单独做“兑换码余额”

不建议新增类似：
- `promo_credits`
- `gift_credits`
- `redeem_balance`

原因：
- 现在的消费逻辑已经很简单，只有一个 `credits`
- 多余额会立刻引入扣减优先级问题
- 会增加 UI 表达复杂度
- 会增加退款、补偿、刷新逻辑复杂度

当前阶段最适合的做法是：
- 所有可消费星尘都落在同一个 `credits` 字段
- 来源通过兑换记录表追踪，而不是通过余额拆账

---

## 与现有订阅体系的关系

当前系统的核心是：
- 免费用户每天保底 `10`
- Awaken 每天保底 `50`
- Depth 每天保底 `100`

兑换码送的 `stardust` 应该视为额外余额。

也就是说：
- 它不是“今天额外加 500，然后明天清零”
- 它应该是正常加到账户余额里
- 之后照常被 chat / echo 消耗

这样最符合直觉：
- 用户兑换到的 `500 stardust`，应该能一直用到花完为止

只要现有每日刷新逻辑是“低于每日保底时补到保底”，而不是“每天强制重置成固定值”，这套模型就成立。

## 后台运营方式

第一阶段不需要做后台页面。

就够了：
- 在数据库里创建兑换码
- 手动设置奖励数量、总上限、有效期、启用状态
- 通过 SQL 或 Supabase 后台维护

例如：
- 春季活动码：`SPRING2026`
- 奖励：`500 stardust`
- 总限制：`500` 次
- 每个用户最多：`1` 次

如果后续活动频率高，再单独做运营后台。

---

## 前端交互建议

入口可以放在：
- 设置页
- 订阅页
- Stardust 说明页

交互尽量简单：
- 一个输入框
- 一个兑换按钮
- 成功后即时显示新增余额
- 失败时显示明确原因

推荐文案：
- 输入兑换码
- 兑换成功，已获得 500 Stardust
- 这个兑换码已兑换过
- 这个兑换码已兑完
- 这个兑换码已失效

不要显示：
- 剩余可兑换次数
- 兑换码内部配置
- 过多后台信息

---

## 风控边界

第一阶段先保持克制，不要一开始做太重。

先不做：
- 设备维度限制
- IP 限制
- 地区限制
- 复杂频率限制
- 渠道归因
- 批量导入卡密系统

如果后续发现有人刷码，再补：
- installation 维度审计
- IP 维度审计
- 渠道字段
- campaign 字段
- metadata 字段

当前最值钱的不是“过度设计”，而是：
- 规则简单
- 结果稳定
- 审计清楚
- 不超发

---

## 推荐结论

对当前 Velune 最合适的兑换码方案是：

- 通用活动码
- 每个码有总兑换次数上限
- 每个码发固定一次性 `stardust`
- 同一用户只能兑换一次
- 必须登录后兑换
- 成功后直接增加 `billings.credits`
- 用兑换记录表做审计
- 用数据库事务保证不超发

这是当前复杂度最低、最稳、最贴合现有账本结构的方案。
